dqlrs notebook

How the notebook flow works

dqlrs notebook starts JupyterLab with one kernel, DQL (Rust). The dqlrs binary is not Jupyter. It carries a small Python kernel, installs JupyterLab into a directory under your home folder, writes a kernelspec that points back at this same binary, and then launches Lab.

A checkout of this repository can also start Lab with ./notebook/start.sh. That script uses the repo’s notebook/ project and registers Python and Rust kernels together. This page is the installed-binary path: dqlrs notebook and dqlrs --notebook.

The whole picture

A cell crosses five stops. dqlrs prepares files and environment, then starts JupyterLab. Lab is the UI. When you open a notebook, Lab starts the DQL kernel, which is a Python process. That kernel keeps a child dqlrs --serve for the life of the notebook and sends each code cell to it. The worker talks to DynamoDB.

Jupyter is downloaded on the first run. The DQL kernel is already inside the binary, copied out every time you start. Cells talk to the dqlrs you invoked, via DQLRS_BIN, so a different dqlrs on PATH is not used.

1. Install

“Install” is two different things. The kernel Python sources ship inside dqlrs. JupyterLab does not. Wheels are large and differ by platform, so the command creates a private virtualenv and installs Jupyter there.

Each launch, before Lab starts:

  1. 1
    Extract the kernel sources and example notebook from the binary.
  2. 2
    Write jupyter_server_config.py and a first kernel.json.
  3. 3
    Create the venv and install JupyterLab if import jupyterlab, ipykernel, jupyter_client fails.
  4. 4
    Rewrite kernel.json so argv uses the venv Python and DQLRS_BIN is this binary.
  5. 5
    Copy dql_notebook_kernel into the venv’s site-packages.
  6. 6
    Start venv/bin/jupyter lab.

Already in the binary

When dql-cli is compiled, rust-impl/crates/dql-cli/build.rs reads the kernel package from the git checkout and turns each file into a string in the binary. A released dqlrs does not need the repository on disk.

The packed files are:

  • notebook/src/dql_notebook_kernel/ — __init__.py, __main__.py, kernel.py, runner.py, serve_client.py, progress.py, magics.py, install.py
  • notebook/examples/getting-started-rust.ipynb

On startup those sources are written to ~/.local/share/dqlrs/notebook/src/dql_notebook_kernel/. magics.py and install.py are for the repo start script (%%dql / %%dqlrs, and writing both kernelspecs). dqlrs notebook still extracts them with the rest of the package. It writes the Rust kernelspec itself, in Rust, and does not call install.py.

What the first run downloads

Into ~/.local/share/dqlrs/notebook/venv (override the parent directory with DQLRS_NOTEBOOK_HOME):

PackageWhy
jupyterlab>=4.2,<5 The notebook UI and the jupyter command. Pulls in the server, client, and their dependencies.
ipykernel>=6.29 The kernel base class. DqlKernel subclasses it and IPKernelApp speaks the Jupyter wire protocol.

The command also checks that jupyter_client imports. That library comes in with Jupyter; it is how Lab manages kernelspecs and connection files. DynamoDB Local, the Python dql package, and any other kernels are left alone.

How the venv is created

ensure_jupyter skips this work when venv/bin/python already exists and this succeeds: 

python -c "import jupyterlab, ipykernel, jupyter_client"

Otherwise it prints Preparing JupyterLab… and builds the venv.

  1. If uv is on PATH: 
    uv venv --no-project --seed --python 3.11 --allow-existing \
  ~/.local/share/dqlrs/notebook/venv
    --seed puts pip into the venv. UV_NO_PROJECT=1 keeps uv from attaching the venv to a nearby pyproject.toml.
  2. If that fails, or uv is missing, it looks for python3.11, python3.12, python3.10, python3, then python, and keeps the first one whose version is at least 3.10. That interpreter runs python -m venv on the same directory.
  3. Packages go in with uv pip install --python <venv python>, and if that fails, with <venv python> -m pip install. The two requirements are jupyterlab>=4.2,<5 and ipykernel>=6.29.

There is no Jupyter if neither uv nor Python 3.10+ is available. The error tells you to install uv or Python 3.11.

Kernel onto sys.path

Lab will start the kernel as python -m dql_notebook_kernel. That only works if the package is importable from the venv interpreter. After Jupyter is ready, dqlrs runs a short Python snippet that deletes and recopies: 

src  = ~/.local/share/dqlrs/notebook/src/dql_notebook_kernel
dest = <venv purelib>/dql_notebook_kernel
       # typically venv/lib/python3.11/site-packages/dql_notebook_kernel

sysconfig.get_path("purelib") is the destination, so the copy lands on that interpreter’s default import path. No PYTHONPATH is set.

Later runs

  • JupyterLab stays installed as long as the import check passes. Delete the venv directory to force a reinstall.
  • The kernel package is extracted from the binary and copied into site-packages on every start, so a newer dqlrs refreshes the kernel without a separate pip install.
  • kernel.json is rewritten every start so its python and DQLRS_BIN match this process.

2. Configure

Configuration is files under the notebook home, plus environment variables on the Jupyter process. Nothing is written to ~/.local/share/jupyter or ~/.jupyter.

Where files live

Default home is $HOME/.local/share/dqlrs/notebook (USERPROFILE on Windows). DQLRS_NOTEBOOK_HOME replaces that path entirely.

Path under the notebook homeRole
src/dql_notebook_kernel/*.py Kernel sources extracted from the binary. Copied into the venv from here.
venv/ Private environment. venv/bin/jupyter is what actually starts Lab. venv/bin/python is the kernel interpreter.
share/jupyter/kernels/dql-rust/kernel.json The kernelspec. This is the file Lab reads to learn the kernel’s name, label, and command.
jupyter_server_config.py Server settings, passed as jupyter lab --config.
jupyter-data/ JUPYTER_DATA_DIR. Jupyter’s own data, kept off the user data dir. The kernelspec is not stored here.
jupyter-runtime/ JUPYTER_RUNTIME_DIR. Connection files for live kernels, and jpserver-*.json records used by dqlrs notebook --shutdown.
jupyter-config/ JUPYTER_CONFIG_DIR. Set so Lab does not read or write your personal Jupyter config. The config file itself is the one next to venv/, passed on the command line.
examples/getting-started-rust.ipynb Copy of the example notebook embedded in the binary.

The working directory you launched from is the notebook root (--notebook-dir and ServerApp.root_dir). If getting-started-dqlrs.ipynb is not already there, one is written. An existing file is left untouched.

Jupyter server config

dqlrs generates jupyter_server_config.py on every start. The root directory is the current working directory, with quotes escaped. --no-browser sets open_browser to false. 

c = get_config()
c.ServerApp.ip = '127.0.0.1'
c.ServerApp.allow_remote_access = False
c.ServerApp.open_browser = True
c.ServerApp.root_dir = '/path/you/started/from'
c.JupyterApp.answer_yes = True
c.KernelSpecManager.allowed_kernelspecs = {'dql-rust'}

Lab is also started with -y, --ip 127.0.0.1, and --notebook-dir set to that same directory. The allow-list is the important line: the launcher offers only DQL (Rust), even if other kernelspecs exist on the machine.

The process command is:

~/.local/share/dqlrs/notebook/venv/bin/jupyter lab \
  -y \
  --config ~/.local/share/dqlrs/notebook/jupyter_server_config.py \
  --notebook-dir "$PWD" \
  --ip 127.0.0.1

--jupyter-port (or --port) adds --port. Arguments after -- are appended as extra Jupyter flags.

The kernelspec

A kernelspec is a directory whose name is the kernel id, containing kernel.json. Here the id is dql-rust and the label on the launcher is DQL (Rust).

The spec is written twice in one run. The first write happens while files are materialized, and the interpreter may still be the placeholder python3 if the venv does not exist yet. After Jupyter is installed, refresh_kernelspec rewrites it with the absolute venv interpreter. Lab only starts after that rewrite. 

{
  "argv": [
    "/Users/you/.local/share/dqlrs/notebook/venv/bin/python",
    "-m",
    "dql_notebook_kernel",
    "-f",
    "{connection_file}",
    "--backend",
    "rust"
  ],
  "display_name": "DQL (Rust)",
  "language": "dql",
  "interrupt_mode": "message",
  "metadata": { "debugger": false },
  "env": {
    "DQLRS_BIN": "/Users/you/.local/bin/dqlrs",
    "DQL_NOTEBOOK_SERVE": "1",
    "DQL_NOTEBOOK_JSON": "1"
  }
}

{connection_file} is a Jupyter placeholder. Lab replaces it with a real path when it spawns the kernel. DQLRS_BIN is std::env::current_exe() for the dqlrs that started the notebook, canonicalized when the OS allows it.

Environment

dqlrs sets variables on itself before it spawns Lab. Rust Command inherits the parent environment, and the kernel inherits Lab’s environment, then applies the env object in kernel.json on top.

  1. 1
    dqlrs notebook sets DQLRS_BIN, region, host, port, dummy keys when --local needs them, and the four JUPYTER_* directories.
  2. 2
    jupyter lab inherits that environment.
  3. 3
    The kernel inherits Lab, then kernel.json sets DQLRS_BIN, DQL_NOTEBOOK_SERVE=1, and DQL_NOTEBOOK_JSON=1.
  4. 4
    dqlrs --serve inherits the kernel and uses DQLRS_BIN as the program to run.
VariableSet byEffect
DQLRS_BIN process env and kernel.json Absolute path of this dqlrs. The kernel runs that file, not whatever dqlrs resolves to on PATH.
DQL_NOTEBOOK_SERVE both, value 1 Rust cells use a long-lived dqlrs --serve worker. 0 would mean one dqlrs -c process per cell. The command always sets 1.
DQL_NOTEBOOK_JSON both, value 1 The one-shot fallback adds --json so rows can render as a table.
JUPYTER_PATH Lab process <home>/share/jupyter. This is how Lab finds kernels/dql-rust.
JUPYTER_DATA_DIR Lab process <home>/jupyter-data
JUPYTER_RUNTIME_DIR Lab process <home>/jupyter-runtime. Connection files and server records.
JUPYTER_CONFIG_DIR Lab process <home>/jupyter-config
AWS_REGION -r / --region, if passed Forwarded to the worker as -r. Otherwise the worker uses the existing AWS_REGION or us-west-1.
DQL_HOST, DQL_PORT --local, or -H / -p When host is set, the worker is started with -H and -p (port default 8000). Unset host means live AWS.
AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY --local, only if unset Dummy values fakeid / fakekey for DynamoDB Local. Existing credentials are kept.

--local does not start DynamoDB Local. If nothing is listening on the host and port, the command prints a warning and Lab still starts. Credentials you already have in the environment (or that the AWS SDK can find) are inherited by the worker.

Notebook files

Code cells in a DQL (Rust) notebook are DQL statements and meta-commands (SELECT, INSERT, ls, and the rest), not Python. The starter notebook copied into the working directory is the embedded getting-started example: create a table, insert rows, and scan.

3. How Jupyter finds the kernel and runs it

Lab never searches the filesystem for dqlrs. It searches for kernelspecs. The spec’s argv is the program it executes. That program is Python. Python then starts dqlrs.

How Lab finds it

Jupyter’s kernel-spec manager looks for kernels/<name>/kernel.json under each entry of the data path. JUPYTER_PATH is prepended to that path. This command sets: 

JUPYTER_PATH=~/.local/share/dqlrs/notebook/share/jupyter

so the search hits …/share/jupyter/kernels/dql-rust/kernel.json. The directory name dql-rust is the kernel id. display_name is what the launcher shows.

KernelSpecManager.allowed_kernelspecs = {'dql-rust'} drops every other spec, including ones in the default user or system Jupyter directories. The New menu and the launcher have a single tile.

--dry-run stops after this setup and runs jupyter kernelspec list with the same JUPYTER_PATH and JUPYTER_DATA_DIR, so you can see dql-rust without opening a browser.

How Lab starts it

Choosing the tile, or opening a notebook whose kernel name is dql-rust, does the standard Jupyter kernel startup:

  1. Lab picks five ZeroMQ ports (shell, iopub, stdin, control, heartbeat) and an HMAC key, and writes a connection file under JUPYTER_RUNTIME_DIR (~/.local/share/dqlrs/notebook/jupyter-runtime). The file looks like this: 
    {
  "ip": "127.0.0.1",
  "transport": "tcp",
  "signature_scheme": "hmac-sha256",
  "key": "<secret>",
  "shell_port": 54158,
  "iopub_port": 54159,
  "stdin_port": 54160,
  "control_port": 54161,
  "hb_port": 54162,
  "kernel_name": "dql-rust"
}
  2. It substitutes that path for {connection_file} in argv and spawns: 
    ~/.local/share/dqlrs/notebook/venv/bin/python \
  -m dql_notebook_kernel \
  -f ~/.local/share/dqlrs/notebook/jupyter-runtime/kernel-<id>.json \
  --backend rust
    The process environment is Lab’s environment plus the spec’s env block (DQLRS_BIN, DQL_NOTEBOOK_SERVE, DQL_NOTEBOOK_JSON).
  3. __main__.py sees --backend rust, sets DQL_NOTEBOOK_BACKEND=rust, and hands the remaining arguments (including -f) to ipykernel: 
    IPKernelApp.launch_instance(kernel_class=DqlKernel)
  4. IPKernelApp reads the connection file and connects ZeroMQ sockets to those ports. Shell carries execute requests. IOPub carries status, display data, and errors back to the notebook UI. Heartbeat is how Lab knows the kernel is alive.

From here, Jupyter’s job is the wire protocol. It does not parse DQL. A code cell arrives as an execute_request whose code field is the cell text.

Inside the Python kernel

DqlKernel in kernel.py implements do_execute. The language metadata says dql (SQL-like highlighting). The backend comes from DQL_NOTEBOOK_BACKEND, which --backend rust set.

On the first cell, if DQL_NOTEBOOK_SERVE is on, the kernel creates one ServeSession. That object owns the dqlrs --serve child. Later cells reuse it. If the worker fails to start or dies, the kernel marks serve as failed and falls back, for that kernel process, to one-shot dqlrs -c (with --json because DQL_NOTEBOOK_JSON=1).

Results go back on IOPub as display_data. Item lists become an HTML table plus plain JSON. Errors go back as an error message. Bulk writes emit progress events; the kernel updates a single display output in place so the notebook shows a progress bar.

Shutting the kernel down calls do_shutdown, which sends {"op":"shutdown"} to the worker and waits for it to exit.

The dqlrs --serve worker

ServeSession resolves the binary from DQLRS_BIN and starts it once: 

$DQLRS_BIN --serve -r "$AWS_REGION" [-H "$DQL_HOST" -p "$DQL_PORT"]

Stdin and stdout are pipes of JSON objects, one per line. The session starts with a ping. A successful reply means the worker is up and its DynamoDB session is ready. Each cell is then: 

{"id":"1","op":"exec","dql":"SCAN * FROM nb_posts"}

The worker may first write progress lines (no ok field), then one result envelope: 

{"id":"1","event":"progress","done":25,"total":100,"phase":"write"}
{"id":"1","ok":true,"kind":"items","items":[{"username":"steve","postid":1}],"partial":false}

kind is items, affected, status, schema, text, or error. The kernel turns that into the cell output. The worker stays up across cells, so connection setup and session state are not repeated per cell. Region, host, port, and AWS credentials are the environment the kernel inherited from dqlrs notebook.

A cell, end to end

  1. You run dqlrs notebook --local in a directory of notebooks.
  2. dqlrs extracts the kernel, ensures the Jupyter venv, rewrites kernel.json with this binary’s path, and starts Lab on 127.0.0.1.
  3. Lab’s kernel path is JUPYTER_PATH/kernels. The only allowed spec is dql-rust.
  4. You open getting-started-dqlrs.ipynb. Lab writes a connection file and runs the venv Python module dql_notebook_kernel with --backend rust and -f pointing at that file.
  5. ipykernel connects back to Lab on the ZeroMQ ports in the file.
  6. The first code cell starts DQLRS_BIN --serve, pings it, then sends the cell text as {"op":"exec","dql":…}.
  7. The reply is rendered in the cell. The next cell reuses the same worker.
  8. Ctrl-C in the terminal stops Lab. From another terminal, dqlrs notebook --shutdown reads jpserver-*.json in the runtime directory and stops the servers you choose.

Commands

dqlrs notebook --local

notebook cannot be combined with --serve or -c. The notebook command is the parent; --serve is the worker the kernel starts later.
